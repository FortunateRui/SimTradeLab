# TD 9-13 Sequential 信号 + 交易策略 · 使用说明

> 运行环境为 PTrade 回测 / 交易引擎。
> 所有可调参数集中在同目录 `config.json`，本文档解释每一项的语义、默认值与取值约束。

## 一、文件与目录结构

```
strategies/my_strategy/
├── backtest.py        # 单文件策略实现（数据 / 信号 / 交易 / 钩子均在此）
├── config.json        # 策略配置参数（**必须存在**，否则启动直接抛错）
├── 说明.md            # 本文档
├── README.md          # TD 9-13 规则与算法定义
└── doc/               # 设计文档与原始论述
```

### 1.1 配置文件路径（仅此一处配置）

`backtest.py` 文件开头定义了一个唯一的常量：

```python
CONFIG_REL_PATH = "TD913_xiongrui/config.json"
```

* 该路径相对于 PTrade 的研究目录根。
* **需要将 `config.json` 上传到 `<research>/TD913_xiongrui/config.json`。**
* 如需迁移/重命名，只改这一行即可，代码其它地方都通过此常量引用。
* 策略在 `initialize` 阶段会先检查该文件是否存在、是否是合法 JSON、是否覆盖了所有必填段，任何一项失败都会直接抛异常终止策略（不再使用内置默认值兜底）。

### 1.2 运行输出目录

策略每次启动都会在 **与 `config.json` 同级** 的位置，按 **策略启动日期** 创建一个输出目录：

```
<research>/TD913_xiongrui/
├── config.json
├── 2023-03-13/                       # 首次用该日期启动
│   ├── strategy.log                  # 控制台日志的完整副本
│   ├── 600519SS.csv                  # 单个标的的所有信号事件
│   ├── 000858SZ.csv
│   ├── ...
│   └── trade_record_600519SS.csv     # 单个标的一笔完整信号到交易生命周期记录
├── 2023-03-13_1/                     # 同日再次启动 → 自动追加 _1
├── 2023-03-13_2/                     # 再次启动 → _2
└── ...
```

规则：
* 目录名 = `<启动日期 YYYY-MM-DD>`。
* 若目录已存在则自动追加 `_1`、`_2`、... 直到不冲突为止，**永远不会覆盖历史结果**。

### 1.3 文件命名规则

| 文件 | 内容 | 命名规则 |
| --- | --- | --- |
| `strategy.log` | 控制台日志的文件副本 | 固定文件名 |
| `<SEC>.csv` | 该标的的所有信号事件（SETUP / COUNTDOWN） | 标的代码去掉所有 `.`；例 `600519.SS` → `600519SS.csv` |
| `trade_record_<SEC>.csv` | 该标的完整交易生命周期记录 | 标的代码去掉所有 `.`；例 `600519.SS` → `trade_record_600519SS.csv` |

所有 CSV 与日志中的时间字段统一格式为 **文本字符串** `YYYY-MM-DD HH:MM:SS`。

## 二、模块架构

| 层 | 关键类 / 函数 | 职责 |
| --- | --- | --- |
| 路径/配置 | `CONFIG_REL_PATH` / `load_config` / `prepare_output_dir` | 配置路径常量；强制校验 config；按启动日期创建输出目录（防覆盖） |
| 日志层 | `StrategyLogger` | 控制台 + 文件双写；统一前缀 `[TD][sec=...][freq=...][dt=...]` |
| 数据层 | `Bar` / `MarketDataFetcher` | `get_history(include=False)` 拉取已收盘 K 线；过滤停牌 |
| 信号层 | `SetupMachine` / `CountdownMachine` / `TDSignalProcessor` | 纯计算；输入是 Bar 序列，输出是事件列表 |
| 信号输出 | `SignalRecorder` | 按 security 分流到独立 CSV |
| 交易输出 | `TradeRecordRecorder` | 仅在 countdown 取消、交易取消、交易卖出等终态写入 `trade_record_<SEC>.csv` |
| 交易层 | `TradeExecutor` | 默认只基于 Buy Countdown 完成买入；买入后跟踪止盈止损 |
| 策略钩子 | `initialize / before_trading_start / handle_data / after_trading_end` | 在 PTrade 允许的接口范围内编排上述模块 |

### 2.1 信号 / 交易的时序约定（重要）

* 数据层采用 `include=False` 拉取历史。**`handle_data` 拿到的最后一根 K 线 = 上一根已收盘 K 线**（日线策略下即昨日）。
* 信号层基于"最后一根 K 线"发出信号，事件 `datetime` = 昨日。
* 交易层基于这些"昨日信号"在**今天盘中**下单；`order_value` 以当日市价成交。

这与交易员视角一致：今天开盘前/盘中跑完昨日收盘后的 TD 分析 → 今天直接入场。

### 2.2 为什么数据要从回测起始日往前取 `lookback_count` 根？

状态机是 **有状态** 的，必须从一段足够长的历史数据中"热身"才能到达当前正确的状态。举例：
* 如果回测从 2023-03-13 开始，策略在第一次 `handle_data` 时会调用 `get_history(count=300, include=False)`，拿到的是 **回测起始日之前** 的 300 根 K 线。
* 这意味着：**Setup 有可能在回测开始前就已经完成**（比如 2023-02-10 完成），相应的 Countdown 在回测开始时已经在进行中。所以 CSV 里第一天（2023-03-13）就可能出现 `BUY_COUNTDOWN_PROGRESS` 事件，它并不是"无中生有"，而是"回测窗口之前已经启动的计数，今日满足进位条件"。
* 这是 **TD 策略固有的行为**：TD 不关心"回测窗口"，只关心连续的 K 线序列。

如果希望从回测开始才允许计数，可以考虑把 `lookback_count` 设得很小（如 15~20），或后续新增一个 `countdown.skip_before_backtest_start` 开关（当前未实现）。

## 三、配置参数详解

`config.json` 按层级组织。所有以 `_` 开头的键视为注释 / 预留说明，加载时自动剥离。
**所有顶层段与其必填字段都必须出现**，否则启动即报错。

### 3.1 `universe`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `securities` | `list[str]` | ✔ | 待跟踪标的列表，非空，PTrade 标准代码格式 |
| `benchmark` | `str` | ✔ | 策略基准（仅影响 PTrade 评价指标） |

### 3.2 `data`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `frequency` | `str` | ✔ | 数据周期；**本策略不支持混合频率**，需与 PTrade 软件中策略周期一致 |
| `fq` | `str` | ✔ | 复权方式：`pre` / `post` / `dypre` / `None` |
| `lookback_count` | `int` | ✔ | 每次 `handle_data` 拉取的 K 线条数。需 ≥ 30 才能覆盖典型 setup+countdown 区段 |
| `min_required_bars` | `int` | ✔ | 有效 K 线（剔除停牌后）不足此数时跳过当根处理 |

### 3.3 `backtest`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `slippage` | `float` | ✔ | 比例滑点，传入 `set_slippage` |
| `limit_mode` | `str` | ✔ | `LIMIT` / `UNLIMITED`，传入 `set_limit_mode` |

### 3.4 `setup`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `enabled` | `bool` | 可选 | 是否启用 Setup 信号（为 `false` 则不会启动任何 countdown） |
| `require_perfect_for_signal` | `bool` | ✔ | 仅"完美 Setup"才输出信号并启动 countdown |
| `extend_record_max` | `int` | 可选 | **预留**：Setup 延伸 / Recycle 最大记录长度 |

### 3.5 `intersection`（**预留**，待后续更新）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `enabled` | `bool` | 是否启用 TD 交叉过滤；当前未实现 |

### 3.6 `countdown`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `enabled` | `bool` | ✔ | 是否启用 Countdown 识别 |
| `type` | `str` | 可选 | `sequence`（已实现）/ `combo`（**预留**） |
| `require_perfect` | `bool` | 可选 | 启用完美 Countdown |
| `tdst_cancel_rule` | `int` | ✔ | TDST 突破取消规则，5 选 1：<br>1. 最高价 > Setup 中最高的收盘价<br>2. 最高价 > Setup 中最高的最高价<br>3. 收盘价 > Setup 中最高的收盘价<br>4. **收盘价 > Setup 中最高的最高价（默认）**<br>5. 收盘价 > Setup 中最高的真实最高价（max(high, prev_close)）<br>Sell Countdown 取反方向 |
| `cancel_on_opposite_setup` | `bool` | 可选 | 反向 Setup 完成时取消当前 countdown |
| `cancel_on_same_setup` | `bool` | 可选 | 同向新 Setup 完成时重置为新 countdown |

### 3.7 `trade`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `enabled` | `bool` | ✔ | 是否启用交易层 |
| `buy_fraction_of_portfolio` | `float` | ✔ | 每次 Buy Countdown 完成后的买入目标金额 = 总资产 × 该比例（例: `0.1` = 总仓位 10%） |
| `min_trade_value` | `float` | ✔ | 目标 / 实际交易金额低于此值时跳过 |
| `min_cash_for_buy` | `float` | ✔ | 可用现金低于此值 → 视为"近似满仓"，禁止买入 |
| `take_profit_on_sell_countdown` | `bool` | ✔ | 是否允许 Sell Countdown 完成信号作为趋势反转止盈。默认 `false`，即 Sell 相关信号保留但不用于交易卖出 |
| `stop_loss_enabled` | `bool` | ✔ | 是否启用止损。默认 `true` |
| `stop_loss_range_multiple` | `float` | ✔ | 止损距离倍数。止损价 = countdown 最低价 K 线的 `low - (high - low) × stop_loss_range_multiple`，默认 `1.0` |
| `profit_target_r_multiple` | `float` | ✔ | 止盈倍数。止盈价 = 买入价 + (买入价 - 止损价) × 该倍数，默认 `1.5` |
| `require_perfect_setup_for_buy` | `bool` | ✔ | 是否要求触发买入的 Setup 必须完美。默认 `false` |

## 四、事件 CSV 字段说明

### 4.1 `<SEC>.csv`（每标的一份）

| 字段 | 说明 |
| --- | --- |
| `datetime` | 事件发生 K 线的时间（字符串 `YYYY-MM-DD HH:MM:SS`） |
| `security` | 标的代码（含 `.`） |
| `frequency` | 周期 |
| `category` | `SETUP` / `COUNTDOWN` |
| `type` | 事件具体类型（见下表） |
| `direction` | `1`-买方向 / `-1`-卖方向 |
| `count` | SETUP 事件为 9；COUNTDOWN 事件为当前计数（1~13） |
| `perfect` | COMPLETE 类型事件是否为完美 Countdown |
| `reason` | CANCEL 事件的取消原因 |
| `setup_type` / `setup_perfect` / `setup_first_dt` / `setup_last_dt` | 关联 Setup 信息，便于从 countdown 事件回溯到发起它的 setup |
| `tdst_threshold` | 当前 countdown 的 TDST 阈值（预计算） |
| `countdown_start_dt` | 当前 countdown 的起始 K 线时间（= 发起它的 setup 第 9 根的时间） |

常见 `type` 值：

| type | 含义 |
| --- | --- |
| `BUY_SETUP` / `BUY_SETUP_PERFECT` | 买入 Setup 第 9 根完成 |
| `SELL_SETUP` / `SELL_SETUP_PERFECT` | 卖出 Setup 第 9 根完成 |
| `BUY_COUNTDOWN_PROGRESS` | 买入计数 +1 |
| `BUY_COUNTDOWN_PLUS_TENTATIVE` | count==12 且 require_perfect 时暂记 `+` |
| `BUY_COUNTDOWN_COMPLETE` / `BUY_COUNTDOWN_COMPLETE_PERFECT` | 买入计数完成（13） |
| `BUY_COUNTDOWN_CANCEL` | 买入计数被取消（`reason`: `opposite_setup` / `same_setup` / `tdst_break_rule_X`） |
| `SELL_*` | 同上，方向相反 |

### 4.2 `trade_record_<SEC>.csv`（每标的一份）

该文件只在一次生命周期到达终态时新增一行：Buy Countdown 取消、Buy Countdown 完成但未买入、买入后卖出。
一个生命周期从 Buy Setup 完成开始。

| 字段 | 说明 |
| --- | --- |
| `security` | 标的 |
| `setup_completed_at` | Buy Setup 完成日期 |
| `setup_is_perfect` | 是否完美 Setup |
| `setup_highest_high` | Setup 阶段 high 的最高价 |
| `count_1_at` ... `count_13_at` | Countdown 第 1 至第 13 个计数日 |
| `count_8_close` | 第 8 个计数日的收盘价 |
| `countdown_completed_count` | 计数终止时的数量 |
| `countdown_is_perfect` | 是否完美 Countdown |
| `countdown_status` | `NORMAL` / `CANCEL_BY_TDST_RULE_[x]` / `CANCEL_BY_OPPOSITE_SETUP` / `CANCEL_BY_SAME_SETUP` |
| `bought` | 是否买入 |
| `buy_reject_reason` | 未买入原因：`TRADE_DISABLED` / `NON_PERFECT_SETUP` / `INSUFFICIENT_CASH` / `MIN_TRADE_VALUE` / `ORDER_REJECTED` / `ORDER_ERROR` |
| `buy_quantity` / `buy_price` / `buy_date` | 买入数量、买入价、买入日期 |
| `stop_loss_price` / `take_profit_price` | 买入后计算出的止损价和止盈价 |
| `sell_price` / `sell_date` / `sell_reason` | 卖出价、卖出日期、卖出原因：`STOP_LOSS` / `PROFIT_TARGET` / `TREND_REVERSAL` / `EXTERNAL_ABORT` |
| `pnl` | 盈亏，按 `(sell_price - buy_price) * buy_quantity` 估算 |

止损价计算：找到 Countdown 阶段实际最低价对应的 K 线，记该 K 线 `low` 与 `high`，则：

```text
stop_loss_price = low - (high - low) * stop_loss_range_multiple
take_profit_price = buy_price + (buy_price - stop_loss_price) * profit_target_r_multiple
```

若 `stop_loss_enabled=false`，策略不会执行止损，但仍会用同一参考价计算止盈价。

## 五、风控规则概览

| 场景 | 规则 |
| --- | --- |
| Buy Countdown 完成但 `available_cash < min_cash_for_buy` | 禁止买入，写入 `trade_record_<SEC>.csv`，`buy_reject_reason=INSUFFICIENT_CASH` |
| Buy Countdown 完成但目标金额 `< min_trade_value` | 禁止买入，`buy_reject_reason=MIN_TRADE_VALUE` |
| 已有未结束仓位又出现 Buy Countdown 完成 | 允许继续买入；每一笔买入独立计算止损价和止盈价，并在 `trade_record_<SEC>.csv` 中单独结束 |
| `require_perfect_setup_for_buy=true` 且 Setup 不完美 | 禁止买入，`buy_reject_reason=NON_PERFECT_SETUP` |
| `order_value` 未返回订单号或抛异常 | 禁止买入，分别记录 `ORDER_REJECTED` / `ORDER_ERROR` |
| 买入后价格触及止损价 | 卖出，`sell_reason=STOP_LOSS` |
| 买入后价格触及止盈价 | 卖出，`sell_reason=PROFIT_TARGET` |
| `take_profit_on_sell_countdown=true` 且 Sell Countdown 完成、仓位盈利 | 卖出，`sell_reason=TREND_REVERSAL` |

实盘环境中，买入后的止盈止损由 `tick_data` 主推回调逐 tick 追踪，买入成交价与数量以 `on_trade_response` 成交回报为准。回测环境中 `is_trade()` 为 `false`，策略降级为：`order_value` 返回订单后按持仓快照近似确认买入，并在后续 `handle_data` 中用上一根已完成 K 线的 `high/low` 判断止盈止损。

## 六、停牌日处理

三层防护，确保停牌日不参与信号计算 / 下单：

1. **盘前过滤**：`filter_stock_by_status(["HALT","DELISTING"])` 剔除当日停牌标的；
2. **盘中复核**：`handle_data` 内通过 `get_stock_status('HALT', today)` 再次确认；
3. **历史清洗**：数据层直接丢弃 `volume<=0` 的 K 线，`SetupMachine` / `CountdownMachine` 收到的永远是有效成交日序列。
