# TD 9-13 Sequential 信号 + 交易策略 · 使用说明

> 运行环境为 PTrade 回测 / 交易引擎。
> 所有可调参数集中在同目录 `config.json`，本文档解释每一项的语义、默认值与取值约束。

## 一、文件与目录结构

```
strategies/my_strategy/
├── backtest.py        # 单文件策略实现（数据 / 信号 / 交易 / 钩子均在此）
├── config.json        # 策略配置参数（**必须存在**，否则启动直接抛错）
├── 说明.md            # 本文档
├── README.md          # TD 9-13 规则与算法定义
└── doc/               # 设计文档与原始论述
```

### 1.1 配置文件路径（仅此一处配置）

`backtest.py` 文件开头定义了一个唯一的常量：

```python
CONFIG_REL_PATH = "TD913_xiongrui/config.json"
```

* 该路径相对于 PTrade 的研究目录根。
* **需要将 `config.json` 上传到 `<research>/TD913_xiongrui/config.json`。**
* 如需迁移/重命名，只改这一行即可，代码其它地方都通过此常量引用。
* 策略在 `initialize` 阶段会先检查该文件是否存在、是否是合法 JSON、是否覆盖了所有必填段，任何一项失败都会直接抛异常终止策略（不再使用内置默认值兜底）。

### 1.2 运行输出目录

策略每次启动都会在 **与 `config.json` 同级** 的位置，按 **策略启动日期** 创建一个输出目录：

```
<research>/TD913_xiongrui/
├── config.json
├── 2023-03-13/                       # 首次用该日期启动
│   ├── strategy.log                  # 精简后的策略复盘日志
│   ├── td_events.csv                 # TD 事件研究元数据
│   ├── event_outcomes.csv            # 事件窗口成熟后的收益/MFE/MAE 元数据
│   ├── position_snapshot.csv         # 开仓/平仓时的轻量仓位快照
│   ├── trade.csv                     # 全部标的完整信号到交易生命周期记录汇总
│   ├── 600519SS/
│   │   └── trade.csv                 # 该标的完整信号到交易生命周期记录
│   ├── 000858SZ/
│   │   └── trade.csv
│   └── ...
├── 2023-03-13_1/                     # 同日再次启动 → 自动追加 _1
├── 2023-03-13_2/                     # 再次启动 → _2
└── ...
```

规则：
* 目录名 = `<启动日期 YYYY-MM-DD>`。
* 若目录已存在则自动追加 `_1`、`_2`、... 直到不冲突为止，**永远不会覆盖历史结果**。

## 二、模块架构

| 层 | 关键类 / 函数 | 职责 |
| --- | --- | --- |
| 路径/配置 | `CONFIG_REL_PATH` / `load_config` / `prepare_output_dir` | 配置路径常量；强制校验 config；按启动日期创建输出目录（防覆盖） |
| 日志层 | `StrategyLogger` | 控制台 + 文件双写；默认只记录启动、盘前摘要、异常、订单失败与交易终态 |
| 数据层 | `Bar` / `MarketDataFetcher` | `get_history(include=False)` 拉取已收盘 K 线；过滤停牌 |
| 信号层 | `SetupMachine` / `CountdownMachine` / `TDSignalProcessor` | 纯计算；输入是 Bar 序列，输出是事件列表 |
| 元数据输出 | `MetadataRecorder` | 写入根目录 `td_events.csv`、`event_outcomes.csv` 与 `position_snapshot.csv`，供论文离线分析 |
| 交易输出 | `TradeRecordRecorder` | 仅在 countdown 取消、交易取消、交易卖出等终态由 `TDStrategyAdapter` 写入 `<SEC>/trade.csv` 与根目录 `trade.csv` |
| 交易层（通用） | `TradeExecutor` + `BuyIntent` / `SellIntent` / `FillInfo` / `TradeExecutorCallbacks` | **完全不感知 TD 9-13 概念**。只接受买卖意图、用 PTrade 真实回报落账、追踪止损止盈、处理除权送股 / 现金分红。对外暴露 `submit_buy / submit_sell / reconcile_pending_orders / check_backtest_exits / check_tick_exits / accrue_dividends / reconcile_position_adjustments / on_trade_response / set_callbacks` 9 个公开 API |
| 策略适配层 | `TDStrategyAdapter` | TD 信号 ↔ 通用交易意图的桥梁：将 BUY/SELL_COUNTDOWN_COMPLETE / CANCEL 翻译成 BuyIntent/SellIntent；接收交易层的成交 / 拒单回调，独占 `trade.csv` 的写入；维护 TD 特有的预检（`require_perfect_setup_for_buy`）和风控参数（`stop_loss_range_multiple`、`profit_target_r_multiple`、`take_profit_on_sell_countdown`） |
| 策略钩子 | `initialize / before_trading_start / handle_data / after_trading_end / on_trade_response` | 在 PTrade 允许的接口范围内编排上述模块；`handle_data` 中用 `g.trade_adapter.execute_for_events(...)` 把信号送入交易层，`on_trade_response` 由 `g.trade_executor.on_trade_response(...)` 触发 reconcile，与回测路径共享同一份写入逻辑 |

### 2.1 信号 / 交易的时序约定（重要）

* 数据层采用 `include=False` 拉取历史。**`handle_data` 拿到的最后一根 K 线 = 上一根已收盘 K 线**（日线策略下即昨日）。
* 信号层基于"最后一根 K 线"发出信号，事件 `datetime` = 昨日。
* 交易层基于这些"昨日信号"在**今天盘中**下单；买入使用 `order_value` 按金额委托，卖出使用 `order` 按该笔仓位数量委托。

这与交易员视角一致：今天开盘前/盘中跑完昨日收盘后的 TD 分析 → 今天直接入场。

### 2.2 为什么数据要从回测起始日往前取 `lookback_count` 根？

状态机是 **有状态** 的，必须从一段足够长的历史数据中"热身"才能到达当前正确的状态。举例：
* 如果回测从 2023-03-13 开始，策略在第一次 `handle_data` 时会调用 `get_history(count=300, include=False)`，拿到的是 **回测起始日之前** 的 300 根 K 线。
* 这意味着：**Setup 有可能在回测开始前就已经完成**（比如 2023-02-10 完成），相应的 Countdown 在回测开始时已经在进行中。所以 CSV 里第一天（2023-03-13）就可能出现 `BUY_COUNTDOWN_PROGRESS` 事件，它并不是"无中生有"，而是"回测窗口之前已经启动的计数，今日满足进位条件"。
* 这是 **TD 策略固有的行为**：TD 不关心"回测窗口"，只关心连续的 K 线序列。

如果希望从回测开始才允许计数，可以考虑把 `lookback_count` 设得很小（如 15~20），或后续新增一个 `countdown.skip_before_backtest_start` 开关（当前未实现）。

## 三、配置参数详解

`config.json` 按层级组织。所有以 `_` 开头的键视为注释 / 预留说明，加载时自动剥离。
**所有顶层段与其必填字段都必须出现**，否则启动即报错。

### 3.1 `universe`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `securities` | `list[str]` | ✔ | 待跟踪标的列表，非空，PTrade 标准代码格式 |
| `benchmark` | `str` | ✔ | 策略基准（仅影响 PTrade 评价指标） |

### 3.2 `data`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `frequency` | `str` | ✔ | 数据周期；**本策略不支持混合频率**，需与 PTrade 软件中策略周期一致 |
| `fq` | `str` | ✔ | 复权方式：`pre` / `post` / `dypre` / `None` |
| `lookback_count` | `int` | ✔ | 每次 `handle_data` 拉取的 K 线条数。需 ≥ 30 才能覆盖典型 setup+countdown 区段 |
| `min_required_bars` | `int` | ✔ | 有效 K 线（剔除停牌后）不足此数时跳过当根处理 |

### 3.3 `backtest`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `slippage` | `float` | ✔ | 比例滑点，传入 `set_slippage` |
| `limit_mode` | `str` | ✔ | `LIMIT` / `UNLIMITED`，传入 `set_limit_mode` |
| `commission_ratio` | `float` | ✔ | 佣金费率，传给 PTrade `set_commission(commission_ratio=...)`；策略内部按同一份费率自算 `buy_commission` / `sell_commission`，使 `trade.csv` 与 PTrade 引擎扣款一致。经手费（万分之 0.487）和印花税（千分之 1，仅卖出）由 PTrade 引擎硬编码，策略也按相同常量参与计算 |
| `min_commission` | `float` | ✔ | 单笔最低佣金，含义与用途同 PTrade `set_commission(min_commission=...)` |

> **手续费同步契约**：PTrade Python API（`get_order` / `get_trades`）**不会回传 `commission` / `stamp_tax` 字段**。策略在 `_settle_pending_*` 中如果 PTrade 没给手续费，会按 `commission_ratio + 万分之 0.487 经手费 +（卖出时）千分之 1 印花税` 自算并写入 `trade.csv`，因此 `commission_ratio` / `min_commission` 必须与 PTrade 引擎的 `set_commission` 调用值保持一致——本策略已在 `initialize` 内做了同步设置，只要不要在用户脚本里另行覆盖就不会失同步。

### 3.4 `setup`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `require_perfect_for_signal` | `bool` | ✔ | 仅"完美 Setup"才输出信号并启动 countdown |

### 3.5 `intersection`（**预留**，待后续更新）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `enabled` | `bool` | 是否启用 TD 交叉过滤；当前未实现 |

## 四、事件 CSV 字段说明

### 4.1 `td_events.csv`

`td_events.csv` 位于本次运行根目录，是论文事件研究的主输入。策略端只记录可复盘的原始事件元数据；事件窗口收益、MFE/MAE 会在窗口成熟后另写入 `event_outcomes.csv`。

| 字段 | 说明 |
| --- | --- |
| `event_id` | 事件唯一 ID，用于和 `event_outcomes.csv` 对应 |
| `datetime` | 事件发生 K 线的时间（字符串 `YYYY-MM-DD HH:MM:SS`） |
| `security` | 标的代码（含 `.`） |
| `frequency` | 周期 |
| `category` | `SETUP` / `COUNTDOWN` |
| `type` | 事件具体类型（见下表） |
| `direction` | `1`-买方向 / `-1`-卖方向 |
| `count` | SETUP 事件为 9；COUNTDOWN 事件为当前计数（1~13） |
| `perfect` | COMPLETE 类型事件是否为完美 Countdown |
| `reason` | CANCEL 事件的取消原因 |
| `setup_type` / `setup_perfect` / `setup_first_dt` / `setup_last_dt` | 关联 Setup 信息，便于从 countdown 事件回溯到发起它的 setup |
| `tdst_threshold` | 当前 countdown 的 TDST 阈值（预计算） |
| `countdown_start_dt` | 当前 countdown 的起始 K 线时间（= 发起它的 setup 第 9 根的时间） |
| `count_1_dt` ... `count_13_dt` | Countdown 各计数日 |
| `countdown_low_dt` / `countdown_low` / `countdown_low_bar_high` | Countdown 阶段最低价 K 线及其 high/low，用于 TD 风险价位复核 |
| `bar_close` / `bar_high` / `bar_low` | 事件 K 线价格 |
| `pre20_avg_amount` | 事件日前约 20 根有效 K 线平均成交额，用于流动性分层 |
| `pre20_volatility` | 事件日前约 20 根有效 K 线日收益波动率，用于波动率分层 |
| `pre20_return` | 事件日前约 20 根有效 K 线区间收益，用于趋势背景分析 |

常见 `type` 值：

| type | 含义 |
| --- | --- |
| `BUY_SETUP` / `BUY_SETUP_PERFECT` | 买入 Setup 第 9 根完成 |
| `SELL_SETUP` / `SELL_SETUP_PERFECT` | 卖出 Setup 第 9 根完成 |
| `BUY_COUNTDOWN_PROGRESS` | 买入计数 +1 |
| `BUY_COUNTDOWN_PLUS_TENTATIVE` | count==12 且 require_perfect 时暂记 `+` |
| `BUY_COUNTDOWN_COMPLETE` / `BUY_COUNTDOWN_COMPLETE_PERFECT` | 买入计数完成（13） |
| `BUY_COUNTDOWN_CANCEL` | 买入计数被取消（`reason`: `opposite_setup` / `same_setup` / `tdst_break_rule_X`） |
| `SELL_*` | 同上，方向相反 |

### 4.2 `event_outcomes.csv`

该文件由策略在事件窗口成熟后写入，离线工具只读取该文件，不再读取 `data/` 行情目录或 parquet 文件。

| 字段 | 说明 |
| --- | --- |
| `event_id` | 与 `td_events.csv` 中事件对应的唯一 ID |
| `event_datetime` | 事件发生时间 |
| `security` / `type` / `direction` | 标的、事件类型、方向 |
| `window` | 事件后观察窗口，当前为 5、20、60、120 根有效 K 线 |
| `matured_datetime` | 该窗口成熟时对应的 K 线日期 |
| `base_close` / `end_close` | 事件日收盘价与窗口末端收盘价 |
| `directional_return` | 方向收益率：`direction * (end_close / base_close - 1)` |
| `mfe` | 窗口内最大有利波动 |
| `mae` | 窗口内最大不利波动 |

### 4.3 `<SEC>/trade.csv` 与根目录 `trade.csv`

`<SEC>/trade.csv` 为每个标的一份；根目录 `trade.csv` 为全部标的汇总。两者字段完全一致。
文件只在一次生命周期到达终态时新增一行：Buy Countdown 取消、Buy Countdown 完成但未买入、买入后卖出。
一个生命周期从 Buy Setup 完成开始。

| 字段 | 说明 |
| --- | --- |
| `datetime` | 事件周期结束的时间 |
| `security` | 标的 |
| `setup_completed_at` | Buy Setup 完成日期 |
| `setup_is_perfect` | 是否完美 Setup |
| `setup_highest_high` | Setup 阶段 high 的最高价 |
| `count_1_at` ... `count_13_at` | Countdown 第 1 至第 13 个计数日 |
| `count_8_close` | 第 8 个计数日的收盘价 |
| `countdown_completed_count` | 计数终止时的数量 |
| `countdown_is_perfect` | 是否完美 Countdown |
| `countdown_status` | `NORMAL` / `CANCEL_BY_TDST_RULE_[x]` / `CANCEL_BY_OPPOSITE_SETUP` / `CANCEL_BY_SAME_SETUP` |
| `bought` | 是否买入 |
| `buy_reject_reason` | 未买入原因：`TRADE_DISABLED` / `NON_PERFECT_SETUP` / `INSUFFICIENT_CASH` / `MIN_TRADE_VALUE` / `ORDER_REJECTED` / `ORDER_ERROR` |
| `buy_order_id` | PTrade 引擎为本笔买入订单分配的订单号；与 PTrade 成交流水中的 `entrust_no` 一致，可直接关联对账 |
| `buy_quantity` / `buy_price` / `buy_date` | **以 PTrade `get_order(order_id)` / `get_trades` 真实成交回报为唯一信源**写入：成交数量、单股成交毛价、真实成交日期与时间。策略不再用快照差或滑点公式估算。两套环境字段映射如下：<br>• PTrade `get_order` 返回 `list[Order]`，取 `Order.filled` 作为数量、`Order.limit` 作为价格兜底；<br>• PTrade `get_trades()` 返回 `dict{order_id: list[list]}`，按位置 `[4]=数量 / [5]=价格 / [6]=金额` 解析；<br>• SimTradeLab `get_order/get_trades` 均按字段名 `business_amount` / `business_price` / `business_balance` 读取 |
| `buy_commission` | 本笔买入实际手续费。**PTrade Python API 不暴露 commission 字段**，策略按 `backtest.commission_ratio` + 经手费（万分之 0.487）自算并写入；当 PTrade / SimTradeLab 回报中携带 commission（含过户费、印花税）时优先采用真实回报值，可直接和 PTrade 流水核对 |
| `entry_value` | 本笔实际开仓金额，等于 `buy_quantity * buy_price`（**毛金额，不含手续费**）；含费净成本 = `entry_value + buy_commission` |
| `stop_loss_price` / `take_profit_price` | 买入后计算出的止损价和止盈价，仅作为触发条件，**不写入成交价** |
| `sell_order_id` | PTrade 引擎为本笔卖出订单分配的订单号；可与 PTrade 成交流水直接对账 |
| `sell_price` / `sell_date` / `sell_reason` | **以 PTrade 真实成交回报为唯一信源**写入：成交毛价、真实成交日期与时间、卖出原因：`STOP_LOSS` / `PROFIT_TARGET` / `TREND_REVERSAL` / `MAX_HOLDING_DAYS` / `EXTERNAL_ABORT`。字段映射同 `buy_*`（`Order.filled` / `Order.limit` / `get_trades` 位置式解析） |
| `sell_commission` | 本笔卖出实际手续费 + 印花税 + 过户费之和。**PTrade Python API 不暴露**，策略按 `backtest.commission_ratio` + 经手费（万分之 0.487）+ 印花税（千分之 1）自算；如果 SimTradeLab 等环境提供 commission 字段则优先采用真实值 |
| `price_pnl` | 价差盈亏（毛），等于 `(sell_price - buy_price) * 卖出数量`，**不扣手续费**。该字段对应"两次成交毛价之差"，与 PTrade 成交流水可直接核对 |
| `dividend_income` | 本笔仓位持有期间归属于本次卖出数量的税后现金分红收益；通过 `get_stock_exrights` 读取 `bonus_ps`，按 `bonus_ps * (1 - 20%) * 持股数量` 累计 |
| `pnl` | 净已实现盈亏 = `price_pnl + dividend_income - 本次卖出对应的买入手续费分摊 - sell_commission`；该字段与 PTrade 净资产变化逐笔对账。若发生部分成交，本行只记录已成交部分对应的费用与收益，剩余数量、剩余分红、剩余手续费继续在 open_trade 中跟踪 |

止损价计算：找到 Countdown 阶段实际最低价对应的 K 线，记该 K 线 `low` 与 `high`，则：

```text
stop_loss_price = low - (high - low) * stop_loss_range_multiple
take_profit_price = buy_price + (buy_price - stop_loss_price) * profit_target_r_multiple
```

若 `stop_loss_enabled=false`，策略不会执行止损，但仍会用同一参考价计算止盈价。

### 4.4 `position_snapshot.csv`

该文件只在开仓、平仓和除权送股同步时写入，用于离线工具还原组合层面的资金占用和仓位变化，不再按每个策略周期逐日输出统计。

| 字段 | 说明 |
| --- | --- |
| `datetime` | 快照发生时间，来自 PTrade 真实成交时间 |
| `event` | `OPEN` / `CLOSE` / `ADJUST`；`ADJUST` 表示策略根据除权除息数据或账户持仓兜底校验同步了逐笔仓位 |
| `security` | 标的代码 |
| `trade_id` | 策略运行内的交易编号 |
| `open_trade_count` | 该标的当前仍在跟踪的未结束仓位数量 |
| `buy_order_id` / `sell_order_id` | 与 PTrade 成交流水关联的订单号 |
| `buy_quantity` / `buy_price` / `buy_commission` / `entry_value` | 本笔当前剩余数量、单股成交毛价、买入手续费、毛金额；发生 `ADJUST` 后数量按 `get_stock_exrights` 的 `allotted_ps` 或账户兜底比例增加，价格按同一比例下调，金额基本保持不变 |
| `stop_loss_price` / `take_profit_price` | 本笔仓位独立止损/止盈价；发生 `ADJUST` 后按除权比例同步下调，保证后续止损/止盈仍按真实剩余股数卖出 |
| `sell_price` / `sell_commission` / `sell_reason` / `pnl` | 平仓时的成交毛价、卖出手续费 + 印花税、卖出原因和净已实现盈亏（已扣除佣金）|
| `total_value` / `available_cash` | 当时可读取到的组合总资产和可用现金；若本地兼容层无法提供则为空 |

周期级胜率、收益率、最大回撤、夏普比率、事件窗口收益等统计结果均由 `tool/thesis_analysis_tool.py` 在策略运行结束后离线生成。

## 五、风控规则概览

| 场景 | 规则 |
| --- | --- |
| Buy Countdown 完成但 `available_cash < min_cash_for_buy` | 禁止买入，写入 `<SEC>/trade.csv`，`buy_reject_reason=INSUFFICIENT_CASH` |
| Buy Countdown 完成但目标金额 `< min_trade_value` | 禁止买入，`buy_reject_reason=MIN_TRADE_VALUE` |
| 已有未结束仓位又出现 Buy Countdown 完成 | 允许继续买入；每一笔买入独立计算止损价和止盈价，并在 `<SEC>/trade.csv` 中单独结束 |
| `require_perfect_setup_for_buy=true` 且 Setup 不完美 | 禁止买入，`buy_reject_reason=NON_PERFECT_SETUP` |
| 买入 `order_value` 未返回订单号或抛异常 | 禁止买入，分别记录 `ORDER_REJECTED` / `ORDER_ERROR` |
| 买入后价格触及止损价 | 卖出，`sell_reason=STOP_LOSS` |
| 买入后价格触及止盈价 | 卖出，`sell_reason=PROFIT_TARGET` |
| `take_profit_on_sell_countdown=true` 且 Sell Countdown 完成、仓位盈利 | 卖出，`sell_reason=TREND_REVERSAL` |
| `max_holding_days_enabled=true` 且单笔交易持仓自然日数达到 `max_holding_days` | 强制卖出，`sell_reason=MAX_HOLDING_DAYS` |

### 5.0 交易层与策略层解耦

策略由两个独立的模块协作完成：

- **`TradeExecutor`（通用交易层）** 不知道任何 TD 概念，只暴露 9 个公开方法
  （`submit_buy / submit_sell / reconcile_pending_orders / check_backtest_exits /
  check_tick_exits / accrue_dividends / reconcile_position_adjustments /
  on_trade_response / set_callbacks`）。所有 TD-specific 逻辑——例如止损止盈如何
  根据 `countdown_low / countdown_low_bar_high` 计算、什么时候要因为非完美 Setup
  而拒绝买入、`trade.csv` 字段如何拼装等——都不在交易层。
- **`TDStrategyAdapter`（策略适配层）** 实现 `TradeExecutorCallbacks` 接口，
  在 `initialize()` 时 `executor.set_callbacks(adapter)` 注册自身，由它独占
  `trade.csv` 的写入。`handle_data` 中调用
  `g.trade_adapter.execute_for_events(...)` 把 TD 事件翻译为
  `BuyIntent` / `SellIntent` 投递给 executor。

通讯契约：

| 数据契约 | 流向 | 关键字段 |
| --- | --- | --- |
| `BuyIntent` | 适配层 → 交易层 | `security`、`fallback_price`、`metadata` |
| `SellIntent` | 适配层 → 交易层 | `security`、`trade`、`sell_reason`、`fallback_price` |
| `FillInfo` | 交易层 → 适配层 | `order_id`、`quantity`、`price`、`commission`、`fill_dt` |
| `TradeExecutorCallbacks` | 交易层 → 适配层 | `on_buy_rejected / on_buy_filled / on_sell_rejected / on_sell_filled / on_position_adjusted` |

如需替换为其他信号体系（例如均线、布林带、其他择时模型），只需新写一个
adapter 实现 `TradeExecutorCallbacks` 即可，`TradeExecutor` 不需要任何修改。

### 5.1 成交结果获取：实盘 / 回测统一走"以 PTrade 真实成交回报为准"

策略不再在下单当时推断成交价 / 成交数量，而是把所有委托挂入 pending 队列，并在每个
`handle_data` 周期开头与结尾调用 `reconcile_pending_orders`，由它通过 PTrade 提供的
`get_order(order_id)` 与 `get_trades(security)` 接口按 `entrust_no` 累加真实成交：

- **`buy_price` / `sell_price`** 直接取 PTrade 成交回报中的 `business_price`（成交毛价）；若回报中只有 `business_balance`，则用 `business_balance / business_amount` 计算。**任何止损价、止盈价、收盘价都不会再被写为成交价。**
- **`buy_quantity` / 实际卖出数量** 直接取 `business_amount`；不再依赖快照差。
- **`buy_date` / `sell_date`** 直接取 `business_time`；不再使用触发信号的 K 线日期，也不再使用下单提交时间。
- **`buy_commission` / `sell_commission`** 单独取 PTrade 订单 / 成交回报中的 `commission`（含过户费、印花税）。
- 一笔订单在 PTrade 异步撮合下可能跨多个周期才完整成交，pending 记录用"已记录数量 / 已记录金额 / 已记录手续费"三个游标累计，**每周期只把"新增成交"的部分写入 trade.csv**，避免重复计费或漏计。
- 当订单状态变成"全部成交"、"部分成交后撤单"或"完全撤单"等终态时，pending 项被摘除；若终态时累计成交量为 0，记录为 `buy_reject_reason=ORDER_REJECTED`。

实盘环境下 `on_trade_response` 收到回报后直接调用同一个 `reconcile_pending_orders`，
回测环境下由 `handle_data` 自动轮询，两条路径写入逻辑完全一致——这意味着无论
SimTradeLab 同步撮合还是 PTrade 异步撮合，trade.csv / position_snapshot.csv
的成交价、成交量、成交日期、手续费四个字段都能与 PTrade 成交流水逐笔对账。

止盈止损触发判断在回测中仍使用上一根已完成 K 线的 `high/low` / `close`；触发时
只是提交订单到 pending，真正的成交结果由 PTrade 真实回报决定。

#### 5.1.1 超时未成交订单保护

PTrade 通常在收盘时会自动撤掉当日未成交的限价单，下一周期 reconcile 看到终态后走
正常清理路径。但若引擎卡死、`get_order` 不返回终态或跨日 limit 单未自动撤，pending
项会永远停在那里，对于卖单还会因 `_has_pending_sell_for_trade` 把后续止损全部封死。
为此 `TradeExecutor` 内置两阶段超时保护：

1. **软超时（`pending_order_timeout_days`，默认 5 个自然日）**：第一次到达阈值时主动
   `cancel_order(order_id)`（兼容 PTrade 的字符串签名与 SimTradeLab 的 Order 对象签名），
   设置 `timeout_cancel_attempted=True` 并打 WARNING；下一周期 reconcile 看到撤单后的
   终态会按"全部撤单 / 部分成交后撤单"的常规路径写入 trade.csv 与 position_snapshot.csv。
2. **硬超时（`pending_order_force_drop_days`，默认 30 个自然日）**：若软超时撤单后仍未拿到
   终态（`get_order` 始终返回非终态），到达硬超时后再尝试一次撤单，强制摘除 pending 项，
   并触发 `on_buy_rejected(intent, "TIMEOUT")` 或 `on_sell_rejected(intent, "TIMEOUT")`，
   同时打 ERROR 提示需人工对账。

行为后果：
- **买单 TIMEOUT**：`TDStrategyAdapter.on_buy_rejected` 会在 `trade.csv` 写入一笔
  `buy_reject_reason=TIMEOUT` 的终结记录，事件链就此闭合。
- **卖单 TIMEOUT**：仓位仍保留在 `open_trades` 中，`pending_sell_orders` 被清空，下个周期
  止损/止盈触发器会重新评估并发起新的卖出意图（不会被 `_has_pending_sell_for_trade` 阻塞）。
- **强制摘除后真的有成交回报到达**：策略不再追踪此订单，trade.csv 不会更新——日志中
  ERROR 会明确提示"请人工对账"，可结合 `tool/reconcile_position_tool.py` 复查账户实盘持仓。

任意一个阈值设为 `<=0` 即视为关闭对应保护；想完全沿用旧的"无限期挂起"行为可同时设为 0。

若账户持仓因送股/转增等除权事件增加，策略会在止盈止损判断前通过 `get_stock_exrights` 读取当天 `allotted_ps`，并按 `1 + allotted_ps` 同步该标的所有未平仓交易的剩余数量、买入价、止损价和止盈价，同时写入 `position_snapshot.csv` 的 `ADJUST` 事件。若接口缺失或字段异常，但账户真实持仓数量仍显著大于策略内部逐笔数量，策略会再按账户持仓差额做兜底同步，避免账户残留送股仓位。

现金分红不会改变持仓数量和止损/止盈价格。策略会在每日持仓检查时通过 `get_stock_exrights` 获取当天除权除息数据，若 `bonus_ps > 0`，则按该标的每笔未平仓交易的当前剩余数量累计税后分红收益。平仓时，`trade.csv` 中 `dividend_income` 单独列出该次平仓对应的分红收益，`pnl` 则包含价差收益和分红收益。

## 六、论文离线分析工具

策略运行结束后，使用 `tool/thesis_analysis_tool.py` 对本次运行目录下的 `td_events.csv`、`event_outcomes.csv`、`trade.csv` 和 `position_snapshot.csv` 进行统计分析。脚本不依赖 PTrade，也不读取 `data/` 行情目录；输出结果默认写入运行目录下的 `thesis_analysis/` 文件夹。脚本会优先使用 `tqdm` 展示进度，未安装时自动降级为普通阶段提示。

离线工具主要生成：

| 输出 | 说明 |
| --- | --- |
| `event_study_summary.csv` | 各类 TD 事件的样本数、方向胜率、窗口收益、MFE/MAE 等摘要 |
| `trade_performance_summary.csv` | 全部、完美 Setup、完美 Countdown、双完美四种交易口径的胜率、盈亏比、收益、回撤、夏普等 |
| `stratified_summary.csv` | 按市场状态、流动性、波动率、信号质量分层后的事件和交易表现 |
| `*.png` | 可直接放入论文的图表 |

策略端不再生成 `<SEC>/statistics.csv` 和 `total_statistics.csv`，避免在 PTrade/SimTradeLab 主循环中执行过多统计计算。

## 七、停牌日处理

三层防护，确保停牌日不参与信号计算 / 下单：

1. **盘前过滤**：`filter_stock_by_status(["HALT","DELISTING"])` 剔除当日停牌标的；
2. **盘中复核**：`handle_data` 内通过 `get_stock_status('HALT', today)` 再次确认；
3. **历史清洗**：数据层直接丢弃 `volume<=0` 的 K 线，`SetupMachine` / `CountdownMachine` 收到的永远是有效成交日序列。
